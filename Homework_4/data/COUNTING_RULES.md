# Neutralization counting rules & status mapping

Generated by `fetch_data.py`. This is the exact logic a TypeScript 
frontend must port to compute `track_status` from OpenF1 at inference 
time so it matches what the model was trained on (FastF1 track_status, 
cross-checked against this same OpenF1 rule during training).

## Status -> category mapping

Applied to the Jolpica `status` string for each driver result row. 
Case-insensitive; trim whitespace first.

```
if status.lower() == "finished": category = "finished"
elif status.lower() == "lapped" or /^\+\s*\d+\s*lap(s)?$/i.test(status):
    category = "lapped"
elif status.lower() in ["did not start", "did not qualify",
                        "did not prequalify", "withdrew"]:
    category = "dns"
elif status.lower() in ["disqualified", "excluded"]:
    category = "dsq"
else:
    category = "retired"   # includes "Not classified" and all
                            # cause-specific strings (Engine, Brakes, ...)
```

## OpenF1 `race_control` neutralization counting rule

**Important discovery from probing real 2023-2026 data: OpenF1's message 
wording is NOT stable across seasons.** 2023-2025 races use the full text 
`SAFETY CAR DEPLOYED` / `VIRTUAL SAFETY CAR DEPLOYED` and represent red 
flags as `category: "Flag", flag: "RED", message: "RED FLAG"`. Starting 
in the 2026 season, VSC messages shorten to `VSC DEPLOYED` / `VSC ENDING`, 
and red flags instead appear as `category: "Other", flag: null, 
message: "RED FLAG - RACE SUSPENDED"`. The rule below is written to match 
both eras. Do not simplify it back to the 2023-era-only wording.

Input: all rows from `GET /v1/race_control?session_key=<race session key>`, 
sorted ascending by `date`. Maintain three running "last counted lap" 
trackers (`lastScLap`, `lastVscLap`, `lastRedLap`), all initially unset.

```ts
for (const r of sortedByDate(messages)) {
  const category = r.category ?? '';
  const msg = (r.message ?? '').toUpperCase();
  const flag = (r.flag ?? '').toUpperCase();
  const lap = r.lap_number;

  // Gate on category === 'SafetyCar' so unrelated messages that merely
  // mention 'safety car' (e.g. penalty/investigation notes, which use
  // category 'Other') can never be miscounted as a deployment.
  if (category === 'SafetyCar' && msg.includes('DEPLOYED')) {
    if (msg.includes('VIRTUAL') || msg.includes('VSC')) {
      if (lastVscLap !== lap) { vscCount++; lastVscLap = lap; }
    } else {
      if (lastScLap !== lap) { scCount++; lastScLap = lap; }
    }
  }

  // flag === 'RED' catches 2023-2025; startsWith('RED FLAG') also catches
  // 2026's category:'Other' representation. startsWith (not includes)
  // deliberately excludes unrelated messages like '... RED FLAG
  // INFRINGEMENT' investigation notes, which never *start* with it.
  if (flag === 'RED' || msg.startsWith('RED FLAG')) {
    if (lastRedLap !== lap) { redCount++; lastRedLap = lap; }
  }
}
```

Notes:

- `...ENDING` messages (`VSC ENDING` / `VIRTUAL SAFETY CAR ENDING`) are 
  ignored entirely -- only `...DEPLOYED` messages count as a new period.
- `SAFETY CAR IN THIS LAP` (category `SafetyCar`, no `DEPLOYED`) is 
  correctly ignored -- it's an informational message, not a new deployment.
- Dedupe is by `lap_number` equal to the previous counted event of the 
  same type -- this collapses duplicate/re-broadcast messages for the 
  same deployment without needing a time-window heuristic.
- `flag` values seen in practice: GREEN, YELLOW, DOUBLE YELLOW, RED, 
  CLEAR, BLUE, CHEQUERED, BLACK AND WHITE; only `RED` is counted here.
- **Known residual mismatch (documented, not fixed):** when the safety 
  car leads the field back out after a red flag ends, race control does 
  not always re-issue an explicit `SAFETY CAR DEPLOYED` message (it's 
  implied by the restart procedure). FastF1's `track_status` stream still 
  shows a fresh transition into status `4` at that point, so on red-flag 
  races the FastF1 safety-car count can be exactly 1 higher than the 
  OpenF1 text-derived count. See data/neutralization_mismatches.csv for 
  which races this affects -- it is a genuine race-control reporting gap, 
  not a bug in either counting rule.
- **Known residual mismatch #2 (documented, not fixed):** occasionally 
  race control re-issues a second `SAFETY CAR DEPLOYED` message for the 
  *same* physical deployment shortly before it comes back in (full SC has 
  no explicit '...ENDING' message the way VSC does -- only an advisory 
  'SAFETY CAR IN THIS LAP' -- so there is no clean signal to reset dedupe 
  state). If that second message lands on a different lap than the first, 
  the lap-based dedupe here counts it as a second deployment while 
  FastF1's `track_status` (which only flips out of `SCDeployed` once, via 
  `AllClear`) counts one continuous period. Net effect: OpenF1's SC count 
  can be exactly 1 *higher* than FastF1's on the affected race -- the 
  opposite direction from residual mismatch #1, so the two do not net out 
  in aggregate; both are genuine, independent race-control artifacts.

## FastF1 track-status counting rule (training labels)

Input: `fastf1.api.track_status_data(session.api_path)` -- called 
directly (one HTTP request) rather than via `session.load()`, which 
issues ~8 requests per race and will trip FastF1's own rate limiter 
(500 calls/h to any single API host, a hard process-global counter -- 
see `fastf1/req.py`) well before a full 2018-2026 run completes. 
`session.api_path` is available immediately after constructing the 
`Session` (it's computed from already-fetched schedule metadata, no 
network call). The season's event schedule is fetched once via 
`fastf1.get_event_schedule(season)` (default backend -- 
`backend='f1timing'` was tried first but silently drops early rounds for 
at least one season, so the default is used instead) and reused for 
every round in that season.

`track_status_data()` returns a `Status` code string per timestamp:

| Code | Meaning |
|---|---|
| 1 | AllClear |
| 2 | Yellow |
| 4 | SCDeployed |
| 5 | Red |
| 6 | VSCDeployed |
| 7 | VSCEnding |

Collapse consecutive duplicate status codes, then count occurrences of 
`4` (safety_cars), `6` (virtual_safety_cars, `7` is the ending marker and 
is never counted), and `5` (red_flags) in the collapsed sequence.

If `track_status_data` is unavailable for a race (raises or returns no 
rows), fall back to `fastf1.api.race_control_messages(session.api_path)` 
(also one request) and apply the *exact same* rule as the OpenF1 rule 
above (both are the same underlying race-control message family; the 
field names just differ in capitalization, which the build script 
normalizes before counting).

**Rate limiting:** if FastF1's `RateLimitExceededError` fires anyway 
(e.g. a concurrent process sharing the same limiter budget), the build 
script treats it as retryable -- it sleeps ~65s and retries, up to 2 
hours total, and never caches a rate-limited attempt as a successful 
(`ok: true`) result. Separately, `SessionNotAvailableError` (observed to 
be transient for a handful of races on a real run -- it succeeded on 
manual retry seconds later) gets a short bounded retry (a few attempts, 
~8s apart) before being treated as a real failure. Both are build-time-
only concerns; neither affects the trained model, the API, or the 
frontend.
